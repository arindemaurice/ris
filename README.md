# RIS | Reliable Internet Solutions

**RIS is a commercial, multi-tenant SaaS platform for independent internet service providers.** It is designed so multiple ISPs can subscribe to RIS and operate separate customer, billing, router, staff, payment, voucher and branding workspaces. It is not a single-provider personal application.

Release **v1.0.0** is the first public RIS release, incorporating the accumulated v2.4.0 operations foundation, v2.5.0 deployment improvements and v2.6.0 payment-settlement/network-monitoring hardening. This release combines the unified RIS public website and workspace UI with a connected FastAPI backend, SQLite local mode, an optional PostgreSQL deployment, provider adapters, RouterOS API-SSL actions, a FreeRADIUS SQL provisioning path and a recurring maintenance worker.

> **First-publication package:** See [INSTALLATION-GUIDE.md](INSTALLATION-GUIDE.md), [PUBLISHING-CHECKLIST.md](PUBLISHING-CHECKLIST.md), [SECURITY.md](SECURITY.md) and [RELEASE-NOTES-v1.0.0.md](RELEASE-NOTES-v1.0.0.md) before deploying.

> **Release status: v1.0.0 initial public release / early access.** The application runs and its automated local test suite passes. It is not yet certified for production ISP operations. Real payment collection, live SMS/email, complete subscriber provisioning, RADIUS accounting/CoA, PPPoE lifecycle, refunds/reconciliation and production security validation still require implementation, credentials and end-to-end lab testing. Do not use this build to promise fully automated internet activation to paying customers until those items are verified.

## 1. Start RIS on Windows (recommended for local testing)

For the full Windows, macOS, Linux distribution, Android, iOS/iPadOS and Docker installation guide, see [INSTALLATION-GUIDE.md](INSTALLATION-GUIDE.md).

The distributable ZIP includes `backend/.env.example` but intentionally contains **no private `.env` file, database, local customer records, generated passwords or runtime caches**. On first start, the launcher runs `backend/setup.py`, which creates a local `backend/.env` with fresh random application secrets, a Fernet key for encrypting ISP gateway/router credentials, a PostgreSQL password and a random initial platform-admin password. Keep that generated `.env` private. It is excluded from Git by `.gitignore` and from release ZIPs.

1. Install Python 3.11 or newer.
2. Extract the ZIP into a folder of your choice and open that extracted project folder in PowerShell.
3. Run `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` and then `.\backend\install_windows.ps1`.
4. When installation finishes, run `.\backend\start_windows.ps1`. It starts the API and background worker. Keep the PowerShell window open.
5. Browse to **http://127.0.0.1:8000**.

The older `backend/run_all_windows.bat` launcher is retained for compatibility; the PowerShell installer/start pair is the recommended Windows path.

Node.js is not required to run RIS.

### Initial RIS platform administrator

- Username: the first-run setup defaults to `Maurice Arinde`; you can enter another platform administrator name during setup. The username is stored in `RIS_BOOTSTRAP_ADMIN_NAME`.
- Email: the address entered during setup remains available as an alternative login identifier.
- Password: open `backend/.env` and copy `RIS_BOOTSTRAP_ADMIN_PASSWORD` generated by `setup.py`. RIS generates a strong random password; it does not ship a shared default password.
- Leave the ISP workspace field blank when signing in as the RIS platform administrator. The platform administrator can enter the configured display name or email in the login field.
- Change the password under **My account** after first sign-in.

Do not paste the bootstrap password or any key into a public repository, chat, screenshot or support ticket. If the ZIP is shared or exposed, regenerate the secrets and administrator password before using that installation.

### First-run setup if `.env` is missing

From PowerShell:

```powershell
cd ris-main\backend
py -3 setup.py
```

The setup script asks for the initial platform-admin email, then creates a new `.env` with random internal secrets and a random platform-admin password. It does not and cannot create Gmail, Africa's Talking, Flutterwave, MTN MoMo, Airtel, MikroTik or RADIUS credentials for you.

## 2. Local development mode

After first-run setup, the generated local `.env` intentionally uses:

```env
RIS_ENV=development
RIS_DEV_SHOW_OTP=true
RIS_PAYMENT_MODE=demo
DATABASE_URL=
RIS_RADIUS_SQL_ENABLED=false
```

In this mode:

- The database is SQLite at `backend/data/ris.db`.
- ISP owner and customer onboarding require two separate six-digit codes: one email code and one SMS code.
- Because no external SMTP/SMS keys are supplied, development-only codes are shown in the local interface/API response. Delivery attempts are recorded in the database without storing raw OTPs or message bodies.
- The demo payment button records a clearly marked simulated payment and updates the local invoice/subscription. It does not collect money or contact a router.
- The maintenance worker runs package expiry and SaaS billing checks at the configured interval.

This mode is for development and demonstrations only. Do not expose this development server to the public internet.

## 3. Public website and sign-in redesign (6 November 2026)

The public RIS website has been rebuilt around the SaaS product itself. Its presentation takes inspiration from the clear product storytelling and dashboard preview patterns of various billing systems, and the ISP-specific operational positioning of formally worked ISP's, while using original RIS copy, layout and branding.

- Public journey: platform overview → capabilities → private ISP workspace setup → onboarding steps → security model → create workspace / sign in.
- The public homepage does **not** display internet package catalogues, speed tiers, validity periods, voucher prices or ISP-specific service offers. Those are configured by each ISP after signing in.
- Each ISP manages its own services and packages, customers, vouchers, routers, payments, branding and staff from its private workspace.
- The separate customer portal displays only the service packages configured by the selected ISP.
- Sign-in, ISP registration, customer access and OTP verification use the updated RIS visual system.
- The public dashboard preview uses illustrative sample figures, not live RIS customer or network statistics.
- The root page includes a visible fallback message if its frontend script fails to load, rather than leaving the visitor on an endless loading screen.


## 2A. Mobile, tablet, desktop and operating-system support

RIS is delivered as a responsive web application and installable Progressive Web App (PWA). Users access the same tenant workspace and account from a supported browser; there is no separate database or account per device. The interface adapts to narrow phone screens, tablet layouts and desktop screens.

### Supported access targets

- **Phones:** Android (Chrome/Edge) and iPhone (Safari).
- **Tablets:** Android tablets and iPadOS (Chrome/Edge/Safari, subject to browser platform rules).
- **Computers:** Windows, macOS and Linux using current Chrome, Edge, Firefox or Safari releases where available.
- **Screen sizes:** layouts are designed to reflow from 320 CSS pixels upward; test real devices and browser zoom before each release.

### Install RIS like an app

1. Deploy RIS behind HTTPS. PWA installation is not available from an ordinary public HTTP site; `localhost` is treated as secure for development.
2. Open the RIS website in the device browser.
3. On Android and desktop Chromium browsers, use the browser's **Install app** or **Add to Home screen** option when offered.
4. On iPhone/iPad, open RIS in Safari, tap **Share**, then **Add to Home Screen**.
5. Launch the RIS icon and sign in normally. The same account and tenant data are loaded from the server.

The service worker caches only the static interface shell and logo. It deliberately does **not** cache `/api/` responses, authentication, billing, payment or customer data. Offline mode displays a connection notice; it does not pretend that live billing, payments, router control or account changes work without a server connection. Push notifications, background sync and native device features depend on browser and operating-system support and are not promised by this release.

### Device testing checklist

- Test public homepage, sign-in, OTP forms, customer portal and every role-specific workspace at phone, tablet and desktop widths.
- Check portrait and landscape orientation, touch targets, keyboard visibility, long tables, dialogs and navigation.
- Confirm no horizontal page overflow at 320, 375, 768, 1024 and 1440 CSS-pixel widths.
- Test install and standalone launch on Android, iOS, Windows, macOS and Linux where supported.
- Test online/offline transitions and confirm API data is never served from the service-worker cache.
- Repeat tests in current Chrome, Edge, Firefox and Safari. Browser support does not mean every browser exposes identical PWA features.

## 3. Workflows available in this build

### RIS platform owner

- Sign in to the separate platform-admin area.
- List ISP workspaces and view their plan/customer counts.
- Activate or suspend an ISP workspace.
- Review RIS subscription invoices, collected amount and outstanding balances.
- Manage your own administrator password.

### ISP onboarding and workspace operations

- Self-register an ISP with a unique workspace slug, owner name, email, phone and password.
- Verify the owner email and phone with separate OTP codes before creating the workspace.
- Create a 14-day trial and attach the initial plan.
- Manage tenant-scoped customers, packages, vouchers, invoices, payments, router inventory and agents.
- Apply plan feature and customer/router-count limits.
- Configure ISP branding and record a custom portal domain.
- Store each ISP's payment gateway credentials encrypted in the database; credentials are not returned by status endpoints.

### Customer portal

- Open `/portal` or `/portal/{workspace-slug}`.
- Create an account with full name, email, phone and password.
- Verify both email and SMS codes before account creation.
- Sign in to the selected ISP workspace.
- Browse packages, create payment requests, review payment/subscription history and view the generated hotspot/PPPoE account credentials.

### Network access lifecycle

After a verified payment, RIS creates a subscription and a per-customer network account. When `RIS_RADIUS_SQL_ENABLED=true` with a configured PostgreSQL/FreeRADIUS database, RIS writes the account into `radcheck` and `radreply`. Session validity, speed, port/device limits and conservative directional byte caps are attached as RADIUS reply attributes. RouterOS RADIUS client configuration can be initiated from the router page after the router's API-SSL credentials and RADIUS target are saved.

## 4. ISP subscription plans and tenant separation

The prototype seeds four RIS SaaS plans: Starter, Growth, Scale and Enterprise. Plan data includes monthly/annual price, customer/router limits and feature entitlements (for example PPPoE, agents and API access). The maintenance worker creates subscription invoices, grants a grace period for unpaid renewals and suspends an ISP workspace after the grace deadline. Zero-priced plans are activated by the billing logic.

Tenant-owned business records are queried using the authenticated user's tenant ID. This is application-level tenant isolation, not a formal PostgreSQL Row-Level Security implementation. PostgreSQL RLS, an external security review and cross-tenant penetration tests are still required before hosting unrelated paying ISPs on one production database.

## 5. Run the PostgreSQL deployment with Docker Compose

The repository includes PostgreSQL 16, the RIS API service and a separate maintenance worker. The Docker image includes both the API and worker code.

1. Install Docker Desktop (Windows) or Docker Engine + Compose (Linux).
2. Edit `backend/.env` and set production secrets and provider values. At minimum:

   ```env
   RIS_ENV=production
   RIS_DEV_SHOW_OTP=false
   RIS_PAYMENT_MODE=live
   PUBLIC_BASE_URL=https://ris.your-domain.example
   RIS_ALLOWED_ORIGINS=https://ris.your-domain.example
   SMTP_PASSWORD=YOUR_GOOGLE_APP_PASSWORD
   AT_USERNAME=YOUR_AFRICAS_TALKING_USERNAME
   AT_API_KEY=YOUR_AFRICAS_TALKING_API_KEY
   RIS_CREDENTIALS_KEY=KEEP_THE_GENERATED_FERNET_KEY
   POSTGRES_PASSWORD=KEEP_THE_GENERATED_RANDOM_PASSWORD
   ```

3. Put the deployment behind an HTTPS reverse proxy (Caddy, Nginx or a managed TLS load balancer). Production session cookies are marked Secure; do not use the production Docker configuration over plain HTTP from the public internet.
4. From the repository root run:

   ```powershell
   docker compose --env-file backend/.env -f backend/docker-compose.yml up --build -d
   ```

5. Check service logs:

   ```powershell
   docker compose --env-file backend/.env -f backend/docker-compose.yml logs -f ris worker db
   ```

The Compose file overrides `DATABASE_URL` to point at the PostgreSQL service and starts the worker separately. PostgreSQL tables are created when RIS starts. **This is a new PostgreSQL database, not an automatic import of an existing SQLite database.** If you already have production data in SQLite, use a reviewed export/import migration and verify every tenant relationship before switching.

### Backup the PostgreSQL database

```powershell
docker compose --env-file backend/.env -f backend/docker-compose.yml exec -T db pg_dump -U ris -d ris > ris-backup.sql
```

Test restore procedures on a separate database before relying on backups. Keep backups encrypted and outside the public web root.

## 7. Configure ISP payment providers

Payment keys belong to the individual ISP business using RIS. Each ISP owner configures its own credentials under **Workspace → Settings**. RIS encrypts these credentials at rest with `RIS_CREDENTIALS_KEY`. Never reuse one ISP's merchant credentials for another ISP.

### Flutterwave

- Add the ISP's Flutterwave secret key and webhook secret hash in Workspace Settings.
- Select Test first, save, then run **Test credentials**.
- Configure the Flutterwave webhook URL shown below in the merchant dashboard:

  `https://YOUR-RIS-DOMAIN/api/webhooks/flutterwave/YOUR-ISP-WORKSPACE`

- The webhook must use the configured `verif-hash` secret. RIS also calls Flutterwave's transaction verification endpoint and checks payment status, reference, amount and currency before activating the customer's subscription.
- Only change to Live after the merchant account is approved and an end-to-end live-value test has reconciled correctly.

Flutterwave's hosted Standard checkout is created through its Payments API and must be followed by transaction verification; a browser redirect by itself does not prove payment. See [Flutterwave API documentation](https://developer.flutterwave.com/docs).

### MTN MoMo Collections (Uganda)

- Register at the [MTN MoMo Developer Portal](https://momodeveloper.mtn.com/) and create an API user, API key and Collections subscription key for the intended environment.
- Save the API user UUID, API key, subscription key, environment (`sandbox` or `production`) and target environment (`mtnuganda`) in Workspace Settings.
- Configure/register the callback host in the MTN developer portal. RIS sends the callback URL in the documented `X-Callback-Url` request header.
- The callback is treated as a notification only. RIS queries MTN's RequestToPay status API and checks success, amount, currency and external reference before activation.
- Test in sandbox before requesting production credentials and testing with a controlled amount.

See the [MTN MoMo Developer Portal](https://momodeveloper.mtn.com/) for current API products, onboarding and environment rules.

### Airtel Money

Airtel credential fields are reserved, but a live Uganda Airtel Money collection adapter is **not implemented in this release**. RIS does not initiate Airtel charges or mark Airtel payments successful. Obtain the applicable country/product API contract and complete a separately tested adapter before enabling it.

### RIS platform subscription payments

The RIS platform owner's own Flutterwave merchant credentials are separate from ISP merchant credentials. Set `RIS_PLATFORM_FLW_SECRET_KEY` and `RIS_PLATFORM_FLW_WEBHOOK_SECRET` in `.env`, then configure this webhook URL at the RIS merchant account:

`https://YOUR-RIS-DOMAIN/api/webhooks/flutterwave-platform`

Do not put these platform credentials into an ISP's workspace settings.

## 8. MikroTik RouterOS API-SSL

Each ISP registers its own router under **Routers & sites**.

1. Use a RouterOS API-SSL service (normally TCP 8729) and install a certificate trusted by the RIS host.
2. Create a dedicated RouterOS API user with only the policies required for resource reads and the specific configuration changes RIS performs. Do not use the router's full administrator credentials.
3. Register router host, port and site in RIS.
4. Save API username/password plus RADIUS server address/shared secret. Router credentials are encrypted at rest and never sent back by list/status APIs.
5. Run **Test**. RIS marks the router online only after a successful TLS/API read.
6. When PostgreSQL/FreeRADIUS are ready, select **Configure RADIUS**. RIS writes the router's RADIUS client entry, turns on RADIUS for hotspot profiles and PPP AAA, enables accounting and configures RouterOS incoming RADIUS messages on UDP 1700.

Keep RouterOS API-SSL certificate verification enabled. Firewall the management port so it is reachable only from the RIS server/VPN. Use a unique RADIUS shared secret per NAS and allow the RADIUS server to receive UDP 1812/1813 from that router.

The RouterOS actions have mocked API tests, but this package has not been tested against your physical RB951, Mercury AP or any live customer router. Run the configuration on a lab router first and inspect the changes before using it on a live network.

## 9. FreeRADIUS and PostgreSQL SQL provisioning

RIS can write customer credentials and reply attributes into FreeRADIUS SQL tables, but it does not install or operate a RADIUS daemon for you.

1. Install a supported FreeRADIUS release on a protected server and configure it to use PostgreSQL.
2. Apply the full PostgreSQL schema shipped with the **exact installed FreeRADIUS version** first. `backend/radius/schema_postgresql.sql` is a minimal lab-compatible subset, not a replacement for the vendor/version schema.
3. Configure and enable the FreeRADIUS PostgreSQL SQL module for `authorize` and `accounting`, then test with the daemon's debug mode (`freeradius -X` or the service's equivalent command).
4. Create database roles with least privilege. FreeRADIUS needs its normal SQL read/write access for `radcheck`, `radreply`, `radacct` and `nas`; RIS needs the minimum insert/update/delete permissions required for provisioning and NAS registration.
5. Point RIS at the same PostgreSQL server using `DATABASE_URL`, then set `RIS_RADIUS_SQL_ENABLED=true` and restart the API and worker.
6. Add the NAS with its private shared secret and confirm its `nasname` matches the source address seen by FreeRADIUS.
7. Save matching RADIUS server IP/shared secret against the router in RIS, test RouterOS API-SSL, then use **Configure RADIUS**.
8. Confirm a test customer authenticates and that accounting records land in `radacct`.

The FreeRADIUS schema reference and a configuration checklist are in [`backend/radius/README.md`](backend/radius/README.md). RIS currently inserts authentication/reply records and removes them at expiry. Reading `radacct` into RIS usage dashboards, exact aggregate quota enforcement and sending live CoA/Disconnect packets for already-connected sessions remain future work. `Session-Timeout` is issued so RouterOS can expire a session at the granted validity boundary.

### Quota and speed notes

- `Mikrotik-Rate-Limit` uses RouterOS's receive/transmit ordering; RIS maps the package upload value first and download second.
- The current data cap is split between `Mikrotik-Recv-Limit` and `Mikrotik-Xmit-Limit`. This is conservative, but an asymmetric traffic profile can leave unused quota. Accurate combined upload+download quota enforcement needs RADIUS accounting aggregation and CoA/disconnect handling, which is not yet implemented.
- Device limits use the FreeRADIUS `Simultaneous-Use` check and RouterOS `Port-Limit` reply attribute. Confirm this behavior with the exact FreeRADIUS and RouterOS versions in the deployment.

## 10. Maintenance worker

The separate `backend/worker.py` process runs `process_maintenance_once()` on the interval in `RIS_WORKER_INTERVAL_SECONDS` (minimum 15 seconds, default 60). It currently:

- Marks expired customer subscriptions expired and removes their `radcheck`/`radreply` records when RADIUS SQL is enabled.
- Creates recurring RIS platform invoices for ISP subscriptions.
- Activates zero-priced subscriptions, marks unpaid renewals past-due and applies a grace period.
- Suspends a tenant after its configured grace deadline.

On Windows, `run_all_windows.bat` launches both the API and worker. On Linux/macOS, use `run_linux_mac.sh`. Docker Compose runs the API and worker in separate containers. Run only one worker per database until a distributed job lock/queue is added.

## 13. Customer operations and platform owner console (v2.4.0)

- ISP staff with the permitted role can add customers, search by name/email/phone/record ID, edit contact details, change service type, suspend and reactivate a customer, and archive a customer.
- Customer archival is a soft-delete. Invoice, payment, subscription and audit history is retained; the record is excluded from the normal active customer list.
- The RIS platform administrator has a global customer view across tenant workspaces, can filter by ISP and search customer/ISP identifiers, create a customer record inside a selected ISP workspace, and suspend/reactivate/archive a record.
- Platform-wide customer actions are written to the audit log under the affected ISP tenant. Tenant staff APIs remain tenant-scoped.
- Platform owner access is available at `/super-admin`. The public site footer links the text “RIS Tech” to this restricted sign-in route.
- The platform administrator can sign in with the configured `RIS_BOOTSTRAP_ADMIN_NAME` or bootstrap email. The generated password is stored only in the private `.env` file.

## 14. Known limitations before commercial production

1. Formal PostgreSQL Row-Level Security (RLS), Alembic versioned migrations, SQLite-to-PostgreSQL data migration, PITR backup/restore drills and a database least-privilege review.
2. Production-grade tenant isolation review and security/penetration testing; the current access boundary is implemented at API query/role level.
3. Production mail/SMS provider accounts, rate limiting by IP/device/phone, durable queue/retry/dead-letter handling and monitoring.
4. End-to-end Flutterwave and MTN sandbox/live merchant tests, payment reconciliation, refund/dispute handling and robust webhook replay monitoring.
5. Airtel Money live Uganda adapter, after its current country-specific integration contract is confirmed.
6. Live RouterOS testing on supported RouterOS versions, multi-router health polling, safe rollback and least-privilege configuration review.
7. FreeRADIUS installation/testing, full-version SQL schema, NAS/radacct accounting ingestion, exact combined data-quota aggregation and CoA/disconnect for active sessions.
8. PPPoE lifecycle testing, voucher redemption/authentication, agent inventory/settlement and subscription/device concurrency handling.
9. Staff invitations and granular permission editor, MFA, password recovery, account verification re-send, session/device management and support-ticket workflow.
10. Production HTTPS proxy configuration, custom-domain/DNS/TLS automation, Redis/BullMQ or equivalent job queue, monitoring, alerts and disaster-recovery runbooks.

Do not store real subscriber passwords or sensitive customer data in this prototype until the production security items have been addressed.

## Captive portal trial workflow (v2.3.0)

Each ISP workspace has its own customer-facing captive portal at `/portal/<workspace-slug>`. The owner or administrator opens **Captive portal** in the workspace navigation to configure the headline, welcome text, brand colours, footer, package visibility, voucher redemption and publishing status. Use **Preview customer portal** to open the public customer view.

### Safe local trial

1. Start RIS locally using the normal Windows, macOS or Linux instructions above.
2. Register an ISP workspace and verify the local email/SMS OTP preview codes.
3. Sign in as that ISP owner and create at least one active **Hotspot** package under Services & packages.
4. Open **Vouchers** and generate a voucher against an active hotspot package if you want to test voucher redemption.
5. Open **Captive portal**, customize the portal and publish it.
6. Open the displayed `/portal/<slug>` link in a private/incognito browser window or a second browser profile. This is the public customer experience.
7. Select **Test purchase**. Enter a test customer's name, review the explicit trial warning and confirm the simulated payment. RIS creates a test customer, invoice, payment, subscription and portal session in the local database.
8. Alternatively, enter an unused voucher code to test redemption. A voucher can be redeemed once.
9. Return to the owner workspace and inspect Customers, Invoices, Payments, Vouchers and the dashboard.

Trial portal purchases and voucher redemption do not call a mobile-money provider, create a RADIUS account, modify a MikroTik router or grant real internet access. The result is a simulated subscription record only. Do not connect a production router to this trial workflow. Demo checkout is disabled in production.

### Trial versus live operation

| Capability | Local trial | Live deployment requirement |
|---|---|---|
| Portal branding and public page | Works locally | HTTPS and public DNS |
| Package catalogue | Uses workspace hotspot packages | Owner-created and tested service catalogue |
| Simulated package purchase | Works locally | Replace with verified provider checkout and signed webhooks |
| Voucher redemption | Activates a trial subscription record | Atomic redemption plus network authorization and abuse controls |
| Router access | Not performed | RouterOS API-SSL, least-privilege router account and tested hotspot profile |
| RADIUS | Not provisioned by public trial flow | FreeRADIUS SQL schema, accounting, CoA/disconnect and tenant-safe policy |
| Customer internet access | Not granted | End-to-end hotspot redirect, authentication and accounting tests |

The captive portal is an initial functional trial slice, not a claim that all production network, payment, PPPoE, reseller, support and monitoring workflows are complete. See `CODE-AUDIT-AND-ROADMAP.md` for remaining work.

## v2.4.0 source-pattern comparison and scope

RIS was compared at the workflow level with PHPNuxBill, a documented open-source MikroTik ISP billing project. PHPNuxBill describes the expected operational sequence: customer chooses and pays for a plan, the subscriber is provisioned on MikroTik or FreeRADIUS, and expired access is removed by a scheduled job. It also documents Hotspot/PPPoE plans, multi-router support, vouchers, payment gateways and staff roles. RIS now has stronger multi-tenant separation and a platform-wide customer console, but does not yet match PHPNuxBill's complete live network lifecycle.

Reference material used for feature comparison (no external source code was copied into RIS):

- PHPNuxBill documentation: https://phpnuxbill.org/docs/
- PHPNuxBill project feature overview: https://github.com/hotspotbilling/phpnuxbill
- MikroTik RouterOS REST API and least-privilege integration guidance: https://manual.mikrotik.com/docs/developer-guides/rest-api/
- FreeRADIUS SQL provisioning and accounting configuration: https://www.freeradius.org/documentation/freeradius-server/4.0.0/tutorials/sql.html

The current source bundle has automated tests for local API workflows and mocks. It has not been verified against a live ISP, payment merchant, production FreeRADIUS daemon or the owner's physical MikroTik router. Do not run disruptive provisioning or reboot actions against the live RB951 until a lab router or isolated test profile is available.
